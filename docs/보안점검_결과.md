# 호스트(Windows) 보안 점검 결과 — 2026-09-09

VirtualBox 를 쓰기 위해 일부 보안 기능을 껐으므로, 무엇이 꺼졌고
무엇이 그대로인지 기록해 둔다. "껐다는 사실을 잊는 것"이 가장 위험하다.

## 종합 판정

주 방어선은 모두 살아 있다. 일상 사용에 문제없는 수준이며,
프로젝트 관점의 외부 노출면도 설계대로 최소화돼 있다.

## 정상 (그대로 유지됨)

| 항목 | 상태 |
|------|------|
| Defender 실시간 보호 | True |
| Defender 변조 방지 | True |
| 맬웨어 정의 최종 갱신 | 2026-09-06 (최신) |
| 방화벽 Domain / Private / Public | 전부 ON |
| UAC | 켜짐 |
| 드라이버 서명 강제 | 유지 (testsigning 설정 없음) |
| RDP | 꺼짐 |

## 의도적으로 끈 것 (VirtualBox 사용 대가)

| 항목 | 상태 | 잃은 보호 |
|------|------|-----------|
| `hypervisorlaunchtype` | Off | Hyper-V, WSL2, Docker Desktop |
| `vsmlaunchtype` | Off | VBS 기반 보안 |
| VBS 상태 | 0 (꺼짐) | 자격증명 격리(Credential Guard) |
| 메모리 무결성(HVCI) | 꺼짐 | 커널 코드 위변조 방지 |

VirtualBox 를 그만 쓸 때 `fix_virtualbox.bat` 의 반대로 되돌리면 된다.

## 프로젝트 관점 — 외부 노출면 (양호)

```
8080  목록에 없음        ✔ nginx 는 VM 내부 127.0.0.1 에만 바인딩
2222  127.0.0.1 전용     ✔ 다른 기기에서 VM SSH 접근 불가
공유기 개방 포트 0개      ✔ 외부 공개는 아웃바운드 터널로만
```

설계 의도가 실측으로 확인됐다. 인바운드 구멍이 하나도 없다.

## 조치 권고

### 1. NetBIOS 139 포트가 실제 IP 에 바인딩 (우선순위: 중)

```
TCP  59.5.137.9:139  LISTENING  PID 4(System)
```

루프백이 아니라 실제 네트워크 인터페이스에 열려 있다.
같은 공유기에 물린 다른 기기에서 접근 가능하다는 뜻이다.
139/445 는 랜섬웨어 확산의 대표 경로였다(WannaCry 등).

공유기가 외부 유입을 막고 있어 인터넷에서 바로 뚫리지는 않는다.
가정용 공유기 환경이면 위험도는 낮지만, 파일 공유를 쓰지 않는다면
꺼두는 편이 낫다.

**끄는 방법** (파일/프린터 공유를 쓰지 않는 경우에만)

```
제어판 - 네트워크 및 공유 센터 - 어댑터 설정 변경
 - 사용 중인 어댑터 우클릭 - 속성
 - "Microsoft 네트워크용 파일 및 프린터 공유" 체크 해제
```

또는 NetBIOS 만 끄려면:

```
어댑터 속성 - IPv4 - 속성 - 고급 - WINS 탭
 - "TCP/IP를 통한 NetBIOS 사용 안 함" 선택
```

### 2. BitLocker 디스크 암호화 없음 (우선순위: 상황에 따라)

```
C:  FullyDecrypted (OFF)
D:  FullyDecrypted (OFF)   ← VM 이미지(.vdi)가 여기 있다
F:  FullyDecrypted (OFF)
```

D: 의 `.vdi` 안에는 `.env`(DB 비밀번호, SECRET_KEY), 데이터베이스,
GitHub 러너 토큰, SSH 키가 들어 있다. 기기를 분실하거나 도난당하면
디스크를 그대로 읽을 수 있다.

- **데스크톱, 집에서만 사용** → 굳이 필요 없다
- **노트북, 외부 반출** → 켜는 것을 강력히 권장

Windows Home 에디션은 BitLocker 대신 "장치 암호화"를 지원할 수 있다.
(설정 - 개인 정보 및 보안 - 장치 암호화)

### 3. Secure Boot 비활성 (우선순위: 하 — 지금은 건드리지 말 것)

```
Secure Boot : False
```

부트킷/루트킷 방어가 약해진 상태다. 다만 **지금 켜지 말 것**을 권한다.

- Windows 용 VirtualBox 드라이버는 Oracle 서명본이라 원칙적으로는
  Secure Boot 와 공존한다.
- 그러나 이번에 드라이버 로딩 문제로 재설치까지 겪었다.
  여기서 부팅 옵션을 또 바꾸면 원인 분리가 어려워진다.
- 시스템이 안정화되고 VM 이 며칠 문제없이 돌아간 뒤에 시도하고,
  실패하면 즉시 되돌릴 수 있도록 UEFI 진입 방법을 미리 확인해 둘 것.

## 재점검 방법

```
scripts\windows\host_security_audit.bat  (우클릭 - 관리자 권한으로 실행)
```

---

## 부록 — "내가 바꾼 것"과 "원래 그랬던 것" 구분

이번 작업으로 **내가 실제로 끈 것** (되돌릴 수 있음):

1. `bcdedit hypervisorlaunchtype` → off
2. `bcdedit vsmlaunchtype` → off
3. `DeviceGuard\EnableVirtualizationBasedSecurity` → 0
4. `DeviceGuard\...\HypervisorEnforcedCodeIntegrity` → 0
5. `Lsa\LsaCfgFlags` → 0
6. DISM: Hyper-V-All / HypervisorPlatform / VirtualMachinePlatform 비활성
7. 코어 격리 - 메모리 무결성 → 끔

**원래부터 그 상태였던 것** (내가 건드리지 않음):

- `Secure Boot: False` — bcdedit/DISM/레지스트리 작업은 UEFI Secure Boot
  설정을 바꾸지 않는다. PC 구입 시점 또는 OS 설치 시부터 꺼져 있었을 것이다.
- `BitLocker: 전부 OFF` — 암호화를 켠 적이 없으면 기본값이 해제 상태다.

이 구분이 중요한 이유: 되돌릴 대상은 1~7 뿐이다.
Secure Boot 와 BitLocker 는 "이번 작업 때문에 나빠진 것"이 아니라
"원래 개선 여지가 있던 항목"이다.

## 되돌리는 방법

```
scripts\windows\restore_security.bat   (우클릭 - 관리자 권한으로 실행)
```

실행하면 VirtualBox 는 작동을 멈춘다(Hyper-V 가 CPU 가상화를 회수).
VM 실습이 끝난 뒤에 실행할 것.
